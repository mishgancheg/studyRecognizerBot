# Развёртывание на сервере: служба systemd за nginx

Проект выкладывается на сервер БЕЗ Docker — обычной службой systemd. На сервере оказываются: рабочая копия
репозитория, служба systemd, задание cron (раз в минуту сверяет копию с веткой на GitHub) и раздел nginx, отдающий
приложение наружу по https.

Навык общий для нескольких проектов и в каждом из них одинаков. Что делает служба этого проекта, чего она требует
от сервера и чем отличается от остальных, описано в [PROJECT.md](PROJECT.md) — прочитай его перед ответом о
службе. Особенности для скриптов собраны в [project.yaml](project.yaml).

Почти всё делают скрипты. Твоя работа — выбрать подкоманду, запустить её и пересказать человеку вывод по-русски.
Не собирай команды ssh и systemctl руками: скрипт `remote.cjs` их уже содержит.

## Единственная команда, которую ты запускаешь

```bash
node .agents/skills/deploy/scripts/remote.cjs <подкоманда>
```

| Чего просит человек | Подкоманда | Что происходит |
|---------------------|------------|----------------|
| завести ключ доступа к репозиторию | `keygen` | Создаёт ключ только для чтения и печатает открытую половину с указаниями. |
| выложить, раскатать, обновить целиком | `deploy` | Полное развёртывание либо повторное: код, настройки, зависимости, шаги проекта, миграции, служба, cron, nginx. |
| состояние, диагностика | `status` | Служба, проверки проекта, рабочая копия, доступность внутри и снаружи, автообновление, раздел nginx. |
| остановить | `stop` | Останавливает службу. |
| запустить | `start` | Запускает службу. |
| перезапустить | `restart` | Перезапускает службу (без переустановки зависимостей). |
| доставить ключи доступа | `push-auth` | Проверяет раздел `access` настроек командой проекта `npm run access:check` и атомарно заменяет `config/access.local.yaml` на сервере (права `0600`), без перезапуска; `--allow-empty` — экстренный отзыв всех ключей. |
| поменять только настройки | `push-config` | Кладёт на сервер `config/local.yaml` и раздел `autoUpdate` (как `deploy/deploy-config.yml`) и перезапускает службу. Ничего не пересобирается, git не трогается. С `--no-restart` только кладёт. Совпавшие файлы не трогает и перезапуск пропускает. |
| зарегистрировать службу в утилите `restart`/`logs`/`stop` | `alias [--alias <имя>]` | Проверяет, есть ли на сервере утилита, считает алиас из имени службы и регистрирует его; занятый алиас — перечень занятых и просьба придумать другой (см. раздел про алиас). |
| дождаться выпуска после `git push` | `wait-update` | Опрашивает сервер каждые 5 с, пока автообновление не дойдёт до отправленного коммита (не дольше 120 с), и печатает итог: обновление, служба, доступность, старт; если за это время сервер до коммита не дошёл — ещё и хвост журнала ошибок `update.cjs`. |
| обновить прямо сейчас | `update` | Запускает `update.cjs --force` — немедленное обновление из ветки. |
| журнал | `logs [N]` | Последние N строк журнала службы (по умолчанию 200). |
| журнал автообновления, ошибки | `updatelog [N]` | Итог последнего обновления (SUCCESS/FAIL), разбор строк `[ERROR]`, хвост журнала ошибок `update.cjs` (след падений) и хвост журнала. |
| оболочка на сервере | `shell` | Открывает bash в каталоге проекта. |
| выполнить команду на сервере | `exec -- <cmd>` | Произвольная команда в каталоге проекта, с нужной версией Node.js в PATH. |
| снести с сервера | `uninstall --yes` | Удаляет службу, cron, раздел nginx и каталог проекта. Необратимо — требует `--yes`. |
| просто зайти по ssh | `ssh` | Печатает готовую команду ssh. |

Ручные действия на сервере (чтение журналов, перезапуск, принудительная пересборка) описаны в `README.md` рядом с
этим файлом.

Пересказывай ровно то, что напечатал скрипт (доступность, вердикт обновления, ошибки) — не придумывай результатов.

## Кратчайший путь выпуска — не дольше двух минут (ЖЁСТКОЕ ТРЕБОВАНИЕ)

Выпуск изменений на сервер — это ровно две команды, и между ними ничего нет:

```bash
git push origin master
node .agents/skills/deploy/scripts/remote.cjs wait-update
```

`wait-update` сам ждёт автообновление и сам проверяет службу и адрес. Запрещено: паузы `sleep` вслепую, отдельные
вызовы `status`, `updatelog` и `logs` после выпуска, повторные проверки «на всякий случай». Если `wait-update` вышел
с ошибкой — только тогда `updatelog`. Перед коммитом гоняй только тесты затронутых файлов; полный прогон тестов —
лишь когда правился код приложения. Правки настроек кладутся `push-config` ДО `git push`, если новый код их читает.

## Общие соглашения для всех проектов

- **Проверка работоспособности — `GET /health`**, без ключа доступа. Её вызывают `deploy`, `status`, `push-config`
  и `wait-update`.
- **Миграции — `npm run migrate`** без доводов: команда проекта обновляет все его базы. Её вызывают `deploy` и
  автообновление.
- **Проверка файла ключей — `npm run access:check -- --file <файл>`**, выпуск ключа — `npm run access:issue-key`.
  Правила проекта (например, обязательные поля клиента) спрятаны внутри его команды `access:check`.
- **Порт приложения — `webServer.port` в `config/local.yaml` навыка.** На этот порт смотрит nginx.

## Общий навык: эталон и синхронизация

Эталон общих файлов — хранилище git на сервере (раздел `skillSource` в `config/deploy.local.yaml`, сейчас
`/opt/node/deploy-skill.git` на сервере ML). Правку общего файла делай в любом проекте и сразу отправляй в эталон;
остальные проекты забирают её сами:

```bash
node .agents/skills/deploy/scripts/sync.cjs status            # что отличается от эталона
node .agents/skills/deploy/scripts/sync.cjs push -m "<что>"   # отправить правку общих файлов в эталон
node .agents/skills/deploy/scripts/sync.cjs pull              # забрать свежие общие файлы из эталона
```

После `push` и `pull` закоммить изменённые файлы вместе с `.sync-base`. Если `pull` или `push` сообщили, что файл
изменён и в проекте, и в эталоне, сведи правки руками и повтори `push`. Новый проект подключается так: скопировать
общие файлы из эталона, написать `project.yaml`, `PROJECT.md`, `config/local.example.yaml`, заполнить два секретных
файла, выполнить `sync.cjs status` — все файлы должны совпадать. Требования к самому проекту: команды
`npm run migrate`, `npm run access:check` и `npm run access:issue-key`, маршрут `GET /health` без ключа, пакет `yaml`
в зависимостях и строка `/deploy/deploy-config.yml` в `.gitignore` (папка `deploy/` на сервере не хранится в git:
`deploy` создаёт её для закрытого файла настроек автообновления, и без этой строки очистка `git clean` при
каждом обновлении удаляла бы файл — отчёты об обновлении перестали бы приходить).

Особенности проекта не вписывай в общие файлы: для них есть `project.yaml` и `PROJECT.md`. Если общему скрипту не
хватает возможности, добавь её как настройку `project.yaml`, а не как ветку под конкретный проект.

## Настройки

Лежат в `.agents/skills/deploy/config/` — два настоящих файла с образцами `*.example.yaml` рядом:

- **`deploy.local.yaml`** — всё о развёртывании. Разделы:\
  `server`, `git`, `site` — куда и чем ходить (обязательны `server.*`, `git.repoUrl`, `git.deployKeyPath`, `site.dns`);\
  `project`, `service`, `node`, `env` — необязательные переопределения каталога, имени службы, версии Node.js;\
  `skillSource` — эталон общего навыка;\
  `autoUpdate` — ложится на сервер как `deploy/deploy-config.yml`, его читает `update.cjs`: ветка, блок
  `telegram.deployReportBot` (`token` и список `chatIds`), список адресов `emails` и необязательный блок `smtp`;\
  `access` — ключи доступа клиентов, ложатся на сервер как `config/access.local.yaml`.
- **`local.yaml`** — файл `config/local.yaml` самого приложения, копируется на сервер **дословно**. Скрипт читает
  отсюда `webServer.port`, признак `webServer.auth.enabled` и значения для подстановок `{{local.<путь>}}` в шагах
  `project.yaml`.

**Переменные окружения на сервере руками не задаются:** файл `.env` рабочей копии каждый `deploy` пишет заново
(`SERVICE_NAME`, `SERVICE_INSTANCE` и `DEBUG` из раздела `env`). Всё, что приложение умеет брать и из переменных
окружения (например, ключ шлюза моделей), на сервере задаётся в `local.yaml`.

Настоящие файлы содержат секреты и могут быть недоступны инструменту чтения — при нужде смотри их через
`node -e "fs.readFileSync(...)"`, а для разбора неполадок пользуйся `status`, `logs`, `updatelog`. Если скрипт пишет,
что какого-то файла или поля не хватает, назови человеку именно его — не подставляй учётные данные наугад.

**Смена настройки после развёртывания.** Эти файлы остаются источником истины. `push-config` кладёт `local.yaml` и
раздел `autoUpdate` и перезапускает службу — это секунды вместо минут; `push-auth` доставляет раздел `access`. Полный
`deploy` нужен, когда изменился `webServer.port` (nginx всё ещё смотрит на прежний порт — команда об этом
предупреждает) или разделы `server`, `git`, `site`, `project`, `service`, `node`, `env`.

## Первое развёртывание — порядок шагов

1. `keygen` — создаёт ключ только для чтения. Передай человеку напечатанную открытую половину и попроси добавить её в
   GitHub (репозиторий → Settings → Deploy keys → Add deploy key, **без** права записи), а путь к закрытой половине
   вписать в `git.deployKeyPath`. Шаг можно пропустить, если в настройках уже указан рабочий ключ.
2. `deploy` — разворачивает всё целиком. Первый запуск идёт несколько минут: ставятся зависимости, выполняются шаги
   проекта, выписывается сертификат домена.
3. `status` — убедиться, что служба работает и адрес отвечает снаружи.

`deploy` сам регистрирует службу в утилите `restart`/`logs`/`stop`, если она есть на сервере (шаг «Алиас службы» в
его выводе). Если он сообщил «ALIAS ЗАНЯТ», доведи регистрацию командой `alias` по правилам ниже.

## Алиас службы в утилите restart / logs / stop

На сервере может стоять утилита restart-logs-completion (проект `D:\DEV\FA\_cur\restart-logs-completion`): команды
`restart <алиас>`, `logs <алиас>`, `stop <алиас>` вместо длинного имени службы. Регистрировать службу в ней нужно при
первичной установке (`deploy` делает это сам) или по просьбе человека — командой `alias`.

Как считается алиас: подчёркивания и дефисы в имени службы делят его на слова, берутся первые буквы слов в нижнем
регистре, так что `my-app--prod` даёт `map`. Скрипт делает это сам, проверяет занятость и регистрирует. Твоё участие
нужно только когда скрипт напечатал `ALIAS ЗАНЯТ` и перечень занятых: придумай другой алиас — он должен хоть чем-то
перекликаться с именем службы и быть как можно короче (до 5 знаков): добавь к первому варианту одну букву из имени
либо возьми другие начальные буквы. Затем повтори:
`node .agents/skills/deploy/scripts/remote.cjs alias --alias <новый>`.
Скрипт сообщит об успехе строкой `ALIAS: '<алиас>' -> <служба> зарегистрирован`; если служба уже зарегистрирована
под другим алиасом, он так и скажет и ничего не изменит; если утилиты на сервере нет — сообщит, и это не ошибка.

## Как устроено развёртывание (пригодится для объяснений и разбора неполадок)

- **Служба systemd, а не Docker.** Файл юнита пишет `.agents/skills/deploy/scripts/srv.cjs` из самого проекта:
  рабочий каталог — копия репозитория, `EnvironmentFile` — её `.env`, запуск — точка входа из `package.json`,
  `Restart=always`. Имя службы — `<имя из настроек>--<экземпляр>`, по умолчанию `<имя из package.json>--prod`.
- **Версия Node.js одна на всех.** Она записана в `.envrc` проекта строкой `nvm use X.Y.Z`; её читают и `srv.cjs`
  (прописывает путь в юнит), и `update.cjs`, и `remote.cjs`. Если этой версии в nvm на сервере нет, `deploy` ставит
  её сам.
- **Ключ доступа прописан в самой рабочей копии.** `deploy` кладёт закрытый ключ в `~/.ssh/<имя>-deploy`, выполняет
  `git config core.sshCommand` и сверяет адрес `origin` с `git.repoUrl`. Благодаря этому автообновление по расписанию
  обращается к GitHub тем же ключом, ничего не зная про переменные окружения.
- **Шаги проекта.** После `npm ci` `deploy` выполняет шаги раздела `deploy` из `project.yaml`, а автообновление —
  шаги раздела `update` (например, установку браузера). `status` дополняет отчёт проверками раздела `status`.
- **Автообновление раз в минуту.** Строка `* * * * * <путь к node> <каталог проекта>/update.cjs >/dev/null
  2>><журнал ошибок>` в личном расписании пользователя сервера (её видно командой `crontab -l`) запускает
  `update.cjs`. Повторный `deploy` находит строку проекта по пути к `update.cjs` и заменяет её, а чужие задания того
  же пользователя не трогает. Обычный вывод запуска выбрасывается: итог и ход обновления `update.cjs` пишет в свои
  журналы. Поток ошибок дописывается в журнал `deploy__<каталог проекта>__errors.log` уровнем выше проекта; при
  обычной работе он пуст. Только в нём остаётся след падения, которое `update.cjs` сам записать не успел (например,
  после сорванной установки зависимостей), с временем и стеком вызовов. О непустом журнале ошибок предупреждает
  `status`, его хвост показывают `updatelog` и неудачный `wait-update`. Появился в ветке новый коммит — копия жёстко
  переводится на него (`git reset --hard` + `git clean -fd`), заново ставятся зависимости (`npm ci`), выполняются
  шаги проекта, служба останавливается, прогоняются миграции и только после их успеха служба запускается снова. При
  ошибке миграции служба остаётся остановленной. Итог уходит в Телеграм и письмом. Рабочая копия на сервере — не
  место для правок: всё изменённое там руками отбрасывается ближайшим сбросом. Файлы из `.gitignore`
  (`config/local.yaml` с секретами, `.env`) очистка не трогает — они переживают любое обновление. Разовый отказ
  обращения к GitHub поломкой не считается: тревожное сообщение уходит только после пяти неудач подряд и только один
  раз, иначе ежеминутная проверка завалила бы почту ложными тревогами.
- **База данных.** Базы создаёт и обновляет `npm run migrate` на каждом развёртывании и на каждом автообновлении.
  Учётные данные — из `local.yaml`; сервер PostgreSQL должен быть уже поднят, а учётной записи нужно право
  `CREATE DATABASE`, иначе первое развёртывание остановится на шаге миграций.
- **nginx.** Раздел для домена рисуется из общих образцов `assets/nginx/site.conf` и `assets/nginx/proxy.conf`:
  подставляются домен, порт, каталог сертификата и параметры из раздела `nginx` файла `project.yaml` (предел тела
  запроса, срок ожидания ответа, дополнительные блоки `location`). Файл кладётся в
  `/etc/nginx/sites-available/<домен>.conf` и включается ссылкой из `sites-enabled`, фрагмент проксирования — в
  `/etc/nginx/snippets/<имя службы>-proxy.conf`, после чего `nginx -t` и перезагрузка. Правь образцы и `project.yaml`,
  а не файл на сервере: `deploy` перезаписывает его, и правка прямо на сервере пропадёт.
  - **Сертификат ищется в трёх местах по очереди:** отдельный сертификат этого поддомена; затем подстановочный
    сертификат родительского домена (для `app.example.com` это `*.example.com` в `/etc/letsencrypt/live/example.com`)
    — его наличие проверяется чтением самого сертификата; и лишь если нет ни того ни другого, выписывается новый
    через `certbot certonly --nginx`.
  - Если certbot не справился (домен ещё не указывает на сервер, закрыт порт 80), раздел nginx не записывается —
    повторите `deploy`, когда домен заработает.
- **Порт наружу не выставляется.** Приложение слушает только `127.0.0.1:<webServer.port>`; снаружи запросы принимает
  nginx на 443 и передаёт их внутрь.

## Разбор неполадок

Неполадки, свойственные конкретному проекту, описаны в его `PROJECT.md`.

- **`Не заполнено git.deployKeyPath` или ключ не найден** — выполни `keygen`, добавьте открытую половину в GitHub
  (только для чтения), впишите путь в `git.deployKeyPath`, затем `deploy`.
- **В поле остался заполнитель** — в `deploy.local.yaml` есть значение в угловых скобках из образца (скрипт
  называет поле). Попроси человека вписать настоящее значение; не придумывай его.
- **Служба не поднимается** — `logs 100`. Частые причины: занятый порт (`webServer.port` в `local.yaml` уже кем-то
  используется на сервере), недоступный PostgreSQL, неверный пароль базы.
- **Снаружи не отвечает, а внутри отвечает** — дело в nginx или сертификате. Проверь `nginx -t`, файл
  `/etc/nginx/sites-available/<домен>.conf`, наличие фрагмента `/etc/nginx/snippets/<имя службы>-proxy.conf` и
  каталог сертификата. Запись `A` для домена должна указывать на этот сервер.
- **Раздел access не прошёл проверку** — сообщение команды `npm run access:check` выше называет нарушение; поправь
  раздел `access` в `deploy.local.yaml` и повтори. Формат ключей, их выпуск, смена и отзыв описаны в документе
  проекта, на который ссылается `PROJECT.md`.
- **Обновления не приходят в Телеграм** — сначала проверь, что на сервере есть `deploy/deploy-config.yml` (его удаляет
  `git clean`, если путь не закрыт `.gitignore` проекта; положить заново — `push-config`). Затем проверь в разделе
  `autoUpdate` блок `telegram.deployReportBot`: его `token` и список `chatIds`. Без токена или без единого чата
  сообщение не уходит. Отказ по каждому чату отдельно виден в `updatelog`. В списке нужны ЧИСЛОВЫЕ номера: положительный
  — личный чат, отрицательный (`-100…`) — группа. Частые отказы Телеграма: «bot can't initiate conversation with a user»
  — человек ещё не нажал «Старт» в боте; «chat not found» — бота не добавили в группу или номер неверный; «the bot can't
  send messages to the bot» — вместо номера указано имя бота.
