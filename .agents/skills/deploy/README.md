# deploy — ручные действия на сервере

Обычный способ управлять развёрнутым проектом — подкоманды скрипта-распорядителя (запускать из корня проекта):

```bash
node .agents/skills/deploy/scripts/remote.cjs <команда>
# keygen | deploy | status | stop | start | restart | update | wait-update [хеш]
# push-config [--no-restart] | push-auth [--allow-empty] | alias [--alias <имя>]
# logs [N] | updatelog [N] | shell | exec -- <cmd...> | uninstall --yes | ssh
```

Ниже те же действия «руками» по SSH — на случай, когда распорядитель недоступен или нужно разобраться в чём-то
тонком. Файл общий для всех проектов; что делает служба конкретного проекта, описано в [PROJECT.md](PROJECT.md).

## Как это устроено

Служба работает на сервере постоянно и отвечает на проверку доступности `GET /health` по адресу домена; она не
зависит от того, включён ли рабочий компьютер.

- **Служба systemd.** Поднимается при загрузке машины и встаёт обратно после любого падения (`Restart=always` без
  ограничения числа перезапусков). Файл службы пишет `.agents/skills/deploy/scripts/srv.cjs`, вычитывая имя, версию
  Node.js и точку входа из самого проекта.
- **Версия Node.js одна на всех.** Записана строкой `nvm use` в `.envrc`; её читают `srv.cjs`, `update.cjs` и
  `remote.cjs`. Если этой версии в nvm на сервере нет, `deploy` ставит её сам.
- **Наружу смотрит только nginx.** Он принимает запросы на 443-м порту под сертификатом Let's Encrypt и передаёт их
  программе, которая слушает лишь `127.0.0.1:<ПОРТ>`.
- **Автообновление раз в минуту.** Рабочая копия на сервере — не место для правок: всё изменённое руками
  отбрасывается сбросом (`git reset --hard` + `git clean -fd`). Файлы из `.gitignore` (`config/local.yaml`, `.env`)
  переживают любое обновление. Разовый отказ обращения к GitHub поломкой не считается: сообщение уходит только после
  пяти неудач подряд и только один раз.

## Откуда берутся имена и значения (ничего не зашито в код)

| Что | Откуда берётся | Обозначение ниже |
|-----|----------------|------------------|
| Адрес, порт, пользователь и ключ SSH | `server.*` в `config/deploy.local.yaml` | — |
| Основа имени службы | `service.name` в `config/deploy.local.yaml` (или имя из `package.json`) | `<ИМЯ>` |
| Имя службы systemd | `<ИМЯ>--<экземпляр>`, экземпляр по умолчанию `prod` | `<СЛУЖБА>` |
| Каталог проекта на сервере | `project.path`, по умолчанию `/opt/node/<ИМЯ>` | `<КАТАЛОГ>` |
| Порт приложения | `webServer.port` в `config/local.yaml` навыка | `<ПОРТ>` |
| Публичный домен | `site.dns` | `<ДОМЕН>` |
| Версия Node.js | `.envrc` проекта (`nvm use X.Y.Z`) | `<ВЕРСИЯ>` |
| Каталог с двоичными файлами Node.js | `~/.nvm/versions/node/v<ВЕРСИЯ>/bin` | `<NODE_DIR>` |
| Шаги, проверки и параметры nginx проекта | `project.yaml` навыка | — |

Быстро посмотреть текущие значения и состояние: `node .../remote.cjs status`.\
Получить готовую команду ssh: `node .../remote.cjs ssh`.

## Чтение журналов

```bash
# Журнал службы, последние строки:
journalctl -o cat --no-pager -n 200 -u <СЛУЖБА>
# Журнал службы в реальном времени:
journalctl -o cat -xefu <СЛУЖБА>

# Итог и журнал автообновления (что сделал update.cjs) — проще через распорядителя:
node .../remote.cjs updatelog
# руками: файлы deploy__<каталог>__status.log / __last_deploy.log / __cumulative.log / __errors.log
# лежат уровнем выше каталога проекта. __errors.log — поток ошибок update.cjs: при обычной работе пуст,
# при падении хранит его след со временем и стеком вызовов.
```

## Перезапуск и остановка

```bash
systemctl restart <СЛУЖБА>
systemctl stop <СЛУЖБА>
systemctl start <СЛУЖБА>
systemctl -l status <СЛУЖБА>
```

Остановка службы не выключает автообновление: как только в ветке появится новый коммит, `update.cjs` соберёт проект
заново и поднимет службу. Чтобы этого не случилось, снимите заодно задание: откройте расписание командой
`crontab -e` и удалите строку с `<КАТАЛОГ>/update.cjs`.

## Смена настроек без пересборки

```bash
node .../remote.cjs push-config               # положить оба файла и перезапустить службу
node .../remote.cjs push-config --no-restart  # только положить; применить потом командой restart
```

Файлы сравниваются по контрольной сумме, заменяется только то, что отличается, прежняя версия остаётся в
`/tmp/pc-prev-<имя файла>`. Если оба файла совпали, перезапуск пропускается. Содержимое никуда не печатается: в нём
пароли и ключи. Руками то же самое выглядит так:

```bash
# на рабочей машине:
base64 -w0 .agents/skills/deploy/config/local.yaml   # скопировать вывод
# на сервере:
echo '<base64>' | base64 -d > <КАТАЛОГ>/config/local.yaml
systemctl restart <СЛУЖБА>
```

Смена `webServer.port` по-прежнему требует полного `deploy`: раздел nginx указывает на прежний порт. `push-config`
об этом предупреждает.

## Ключи доступа (push-auth)

Ключи клиентов хранятся в разделе `access` файла `config/deploy.local.yaml`. При включённой защите
(`webServer.auth.enabled` в `config/local.yaml`) `deploy` проверяет раздел командой проекта `npm run access:check` и
доставляет его на сервер как `config/access.local.yaml`. Команда `push-auth` делает то же без перезапуска службы:
атомарно заменяет файл с правами `0600`, служба перечитывает его сама. Формат файла, выпуск, смена и отзыв ключей
описаны в документе проекта, на который ссылается [PROJECT.md](PROJECT.md).

## Принудительное обновление (update.cjs -f)

Заставить сервер немедленно забрать ветку, переставить зависимости, прогнать миграции и перезапустить службу, не
дожидаясь ежеминутной проверки. Ключ `-f` — короткая запись `--force`:

```bash
cd <КАТАЛОГ> && PATH=<NODE_DIR>:$PATH ./update.cjs -f
# или просто:
node .../remote.cjs update
```

Приставка `PATH=<NODE_DIR>:$PATH` обязательна: системный `node` на сервере обычно старый, а `npm` из nvm им попросту
не запускается. В задании cron то же достигается полным путём к `node` из nvm, а каталог для `npm` и прочих своих
команд `update.cjs` дописывает в PATH сам.

## Переустановка службы systemd

```bash
cd <КАТАЛОГ>
PATH=<NODE_DIR>:$PATH node .agents/skills/deploy/scripts/srv.cjs delete
PATH=<NODE_DIR>:$PATH node .agents/skills/deploy/scripts/srv.cjs install
cat /etc/systemd/system/<СЛУЖБА>.service
```

## Проверка nginx и доступности снаружи

```bash
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:<ПОРТ>/health     # на самой машине
curl -sS -o /dev/null -w '%{http_code}\n' https://<ДОМЕН>/health             # снаружи

nginx -t && systemctl reload nginx
cat /etc/nginx/sites-available/<ДОМЕН>.conf
cat /etc/nginx/snippets/<ИМЯ>-proxy.conf
certbot certificates | grep -A3 "<ДОМЕН>"
```

Раздел nginx собирается из общих образцов `.agents/skills/deploy/assets/nginx/site.conf` и
`.agents/skills/deploy/assets/nginx/proxy.conf` с параметрами из `project.yaml`. Правьте их и запускайте `deploy` —
прямая правка файла на сервере переживёт лишь до следующего развёртывания.

## База данных

```bash
cd <КАТАЛОГ> && PATH=<NODE_DIR>:$PATH npm run migrate   # прогнать миграции всех баз проекта
```

Базы проекта создаются самими миграциями, поэтому заранее заводить их не нужно — достаточно работающего сервера
PostgreSQL и верных учётных данных в `config/local.yaml`. Какие базы у проекта, какая нужна версия PostgreSQL и как
ограничить команду одной базой, описано в [PROJECT.md](PROJECT.md).

## Полный снос с сервера

```bash
node .agents/skills/deploy/scripts/remote.cjs uninstall --yes
```

Удаляет службу, задание cron, раздел nginx, фрагмент проксирования и каталог проекта. Сертификат и внешние каталоги
данных службы остаются: сертификатом могут пользоваться другие проекты на этой же машине, а данные удаляются только
осознанно.
